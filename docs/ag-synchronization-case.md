# AGの許可事象の同期位置に関する事例

対象は [AG Record-guided 試行2](../llm-responses/AG/record-guided/run-02.md) と
[保存コード候補](../revisions/AG/record-guided/run-02.lts) である。
同期位置の懸念は試行2・6に認められた。以下は試行2の説明である。

部屋への入室を拒否した後の順序は、引数を省略すると次のようになる。

```text
VISITOR: deny_A -> arrive_Hall -> ...
HALL:    deny_A -> ctrl_arrive_Hall -> arrive_Hall -> ...
```

ctrl_arrive_HallはVISITORの別の分岐にも現れるため、両プロセスの共有事象となる。
共有事象は双方が実行可能な場合だけ同期発火する。deny_A後にHALLは許可事象を待ち、
VISITORは到着事象を待つため、この分岐の到着動作が進まない。

本文・回答書には、著者が試行2をMTSAで再合成して動作を確認したところ、
施錠・解錠を繰り返す遷移のみが可能となり、業務動作が進行しない状態を確認した旨を報告している。
発火可能な事象は残るので、形式的な遷移不能と業務上の進行停止を区別する。

## 証拠の収録範囲

原ログ、保存されたモデル候補と該当分岐を掲載している。
上記の手動動作確認に対応する制御器のエクスポート／操作履歴は、今回整理した保存資料から
一意に特定できておらず、このページで独立した実行証跡として公開したものではない。
過去の別の予備調査のAUT出力を、この手動確認の証拠として流用していない。
原稿の報告と、ここで直接追跡できるコード上の根拠を区別する。

## 再確認の観点

保存モデルを同じ設定のMTSAで合成し、自動的な追加修復が行われていないことと、
対象controller宣言を確認する。その制御器で、入場・入室・退出・入室拒否後のホール復帰の
各事象列を実行できるかを確認する。新規許可の導入や合成成功だけでは必要動作の維持を判断しない。
