# 補足B：評価モデルの改変

本文5.1節から移した5モデルの説明と、入力ソースに基づく変数・事象・要求の対応を示す。改変前モデルへの復元を一律の正解とせず、実現不能な入力モデルの要求を維持する追加制御の設計を評価する。

## 規模パラメータと要求

| 本文表記 | 主なパラメータ・状態変数 | 入力モデルで維持する要求 |
|---|---|---|
| AT(2,2) | `N=2`は航空機数、`K=2`は高度段階数。`P`は航空機ID、`h`は待機中の高度。 | 高度・進入の競合回避と、着陸処理中の他要求の排他。合成仕様に`nonblocking`を含む。 |
| AG(2,2) | `N=2`は人数カウンタの上限。`HALL[n]`と`ROOM_A[n]`が人数、扉プロセスが施錠状態を表す。`TH_HALL=TH_A=2`。 | `arrive_Hall[TH_HALL]`と`arrive_A[TH_A]`が発生しない。閾値の人数に達すること自体を禁止する式である。 |
| AM(2,5) | `N=2`は利用者数、`K=5`はデータ（仮想サーバ）数。`ID`は利用者、`data`は対象データ。`Public_Data=1..1`。 | 管理者の拒否禁止、一般利用者の非公開データ転送禁止・公開データ拒否禁止、要求処理の排他。 |
| BW(2,2) | `N=2`はチーム数、`K=2`は審査段階数。`ID`はチーム、`s`は審査段階。 | 拒否処理の履歴と`approve`／`refuse`の整合、および他チームへの割当ての排他。合成仕様に`nonblocking`を含む。 |
| KIVA | `PodNum=2`は棚位置の数。`Area`は出荷・箱取得・品目取得・梱包エリア。各ロボットの現在位置と要求処理履歴をモデル化する。 | 搬送・補充・出荷等の順序制約と、同じ棚・作業エリアでの2台の同時存在禁止。 |

KIVAのソースには`RobotNum=1`という宣言もあるが、合成対象の`KIVA_System`は`robot1`と`robot2`を明示的に並列合成している。実験のロボット構成はこの合成式に基づき、宣言名だけから1台と解釈しない。

成功指標は本文で定めた制御器合成であり、表の要求を満たすことと、業務上必要なすべての動作を実行できることは区別する。任意の到達目標や活性を事後に満たしたと判定するものではない。

## AT：Air Traffic

航空機の着陸調整を表す。`requestLand`と`extendFlight`は制御不可能、`descend`と`approach`は制御可能である。着陸処理が完了するまで別の着陸要求を受け付けない安全性要求`RequestMonitor`を追加した。既存の航空機・応答プロセスを保持し、新しい要求に対して許可機構を設計する事例である。

## AG：Art Gallery

部屋・通路の人数と扉の施錠を表す。入室許可事象集合`AllowAction`を制御可能集合から除いた。許可事象と扉プロセスは残し、制御可能なのは`LockAction`である。これにより環境が先に許可・入室を発生させる状況を作る。

## AM：Access Management

利用者の要求、データ選択、可否判定、フィルタ、転送、処理完了を表す。`request[ID]`は制御不可能で、選択・可否・拒否・転送・フィルタ・完了などは`ControllableActions`に含む。利用者の要求処理が終わるまで他方の新たな要求を禁止する`P_NOT_OTHER_REQUEST_01`と`02`を要求集合に追加した。

## BW：Bidding Workflow

チームへの書類割当てと段階的審査を表す。外部審査者のプロセスを環境へ並列合成し、審査中に別チームへ次の書類を割り当てない排他要求を追加した。さらに`assign`を制御可能集合から除き、`refuse`と`approve`だけを制御可能にした。今回のゲームには敗北領域内にMixed Stateがなく、候補生成の対象外となった。

## KIVA：倉庫搬送

2台のロボット、作業エリア、搬送・補充・出荷要求のプロセスを並列合成する。移動事象と`replenish`・`bring`を制御可能集合から除き、同じ棚・作業エリアへの同時存在を禁止する`P_NO_COLLISION`を追加した。候補は69,318件生成されたが、本文の計算環境・時間上限では介入・再合成を完了しなかった。
